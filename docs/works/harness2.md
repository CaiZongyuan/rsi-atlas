## 一句话

把「运行框架」本身当成可训练对象：用**行为对比**替代缺失的验证器，用**经验库**替代不可迁移的任务特定编辑。

## 它要解决的问题

论文先摆了一个前提：智能体的能力不只取决于模型，还取决于**运行框架**——提示词、记忆、技能、工具与编排<sup>（§1）</sup>。同一个模型换一套框架，表现可以差很多。

把 RSI 用到这一层，开放世界会立刻遇到两个障碍：

1. **没有可靠的验证器。** 任务在框架设计阶段看不见，测试时又是全新的；没有标准答案，就没有一个可信的信号告诉你“这次改对了”。
2. **改进不迁移。** 针对某个任务调出来的框架，换个任务就失效；随着任务分布漂移，直接继承上一条高度定制的框架，反而会带来噪声。

论文的核心问题因此变成一句话：**递归自我改进能不能既改进当前的框架，又改进“未来怎么改进框架”？**

## 机制：两层递归

Harness² 把系统拆成两个对象：

- **执行运行框架**（记作 H）：真正去干活的配置，含 8 个可编辑组件——系统提示词、护栏、记忆、技能、工具指导、脚本、子智能体、中间件插件。每个组件以文件形式挂载。
- **改进运行框架**（记作 R_t）：指导“怎么改”的那一层。任务期间固定，任务结束后更新。

对应两层递归：

| 层级 | 做什么 | 更新时机 |
|---|---|---|
| 任务级递归 | 优化当前任务的执行框架 H | 任务进行中 |
| 构建级递归 | 更新改进框架 R_t 里的经验库 | 每个任务结束后 |

### 任务级：提议 → 探测 → 组合

这是全文最值得看的部分。因为没有验证器，它不比“谁答对了”，而是比**行为**：

1. **提议**：先跑一次参考执行 $e^0$，看清当前框架“怎么做事”。然后提两个候选——一个针对**不变性缺陷**（规划、工具使用、上下文管理、委派这类跨领域通病），一个针对**领域特定知识**（当前任务的流程、约束、格式）。
2. **探测**：在相同模型、相同环境下，把两个候选各自跑一遍同一任务，比较轨迹与交付物相对参考执行的变化——哪些行为被修好了、哪些没变、哪些被弄坏了。
3. **组合**：读完整套证据后，选择性地合并、修订、采用某一个、或者干脆保留原框架。每个决策都要挂到具体观察上，而不是假设“分数会涨”。

这套步骤有个明确的边界：**它验证的是行为，不是正确性**。论文自己也说，执行随机性和模型共有偏差会限制证据的可靠性<sup>（§2.2.1）</sup>。

### 并行与顺序

- **并行递归**：一次收集 k 个候选池，开 k 个独立组合会话，各自产出后继框架并执行。宽度换多样性。
- **顺序递归**：串 k 个对比步骤，每一步都带着前面的框架和执行历史继续改。深度换收敛。

k=1 时两者都退化成单个对比步骤。k>1 时由**匿名选择器**在交付物之间挑一个——它看不到产生这个交付物的框架，也不能合成新内容，只能选已有的。

### 构建级：经验库

每个任务结束后，系统回看完整的改进记录：参考执行、候选、探测结果、组合决策、最终采用的东西。反思只保留**被执行对比支持**的经验，写成一条库条目：

```
一条库条目 = 一个可执行框架 + 一份 EXPERIENCE.md（适用情形、经验、支持证据）
```

下一个任务仍然从共同的初始框架 H₀ 开始，但由更新后的 Rₜ₊₁ 指导。注意这里的设计：**不是自动继承上一个任务的框架，而是通过“提议”选择性复用**。这一点直接回应了“任务特定编辑不迁移”的问题。

## 结果

主实验用两个开源执行框架（OpenCode、Codex）× 两个模型（Gemini 3.5 Flash、GLM-5），在三个专业基准上评：WorkBuddy-Bench（Code / Web / Office）、JobBench、LAB（法律）。

以 Gemini 3.5 Flash + OpenCode 为例<sup>（表 1）</sup>：

| 方法 | 平均分 | 平均步数 |
|---|---|---|
| OpenCode（原始框架） | 72.4 | 25.4 |
| Meta-Harness（离线搜索） | 76.4 | 28.8 |
| Harness Scaling（逐实例改） | 75.3 | 22.3 |
| **Harness²（k=1）** | **77.5** | **21.9** |
| + 任务级递归（k=5 并行） | +3.3 | −0.8 |

论文摘要给的三个数：WorkBuddy-Bench 最多 **+11.5 分**、JobBench **+4.5 分**、LAB **+11.8 个百分点**。另外两个值得记的：

- **k 从 1 加到 5**，JobBench 的增益从 4.5 涨到 7.5，WorkBuddy-Bench 从 5.1 涨到 8.4；并行递归把 WB 的 Code 从 76.5 推到 80.8、Office 从 79.5 推到 83.4。
- **同一模型兼任编辑器和执行器也能涨**：Opus 5 在三个基准上分别 +3.3 / +5.5 / +3.0，GLM-5 在 LAB +13.7。意思是这套方法不依赖“找个更强的模型来改”。

### 消融

| 配置 | WorkBuddy-Bench | JobBench |
|---|---|---|
| 完整 Harness² | 77.5 | 36.0 |
| 去掉经验库 | 74.4 (−3.1) | 34.2 (−1.8) |
| 去掉范围分工（两个通用编辑器） | 74.6 (−2.9) | 32.3 (−3.7) |
| 去掉组合（二选一） | 75.9 (−1.6) | 34.1 (−1.9) |

三个组件都有贡献，其中“把编辑器按不变性 / 领域分工”在 JobBench 上影响最大，“经验库”在 WorkBuddy-Bench 上影响最大。

## 和 RSIGym 比，差在哪

两篇都在讲“让智能体自己改自己”，但改的东西和判断依据完全不同：

| | RSIGym | Harness² |
|---|---|---|
| 改什么 | 数据 + 训练配方 + 执行框架（三选或全开） | 只改执行框架的 8 个组件 |
| 判断依据 | 官方基准分（开发期可反复自评） | 没有验证器，只比行为差异 |
| 递归层级 | 单轮：一次运行、一次提交 | 两层：任务内改框架，任务间改“怎么改” |
| 评测 | 5 个通用基准，18–42 次运行 | 3 个专业交付物基准，4 种模型×框架配置 |
| 成本口径 | 平台计费（$500/次） | 总 token（执行 + 改进都算） |

一句话对比：**RSIGym 用“能测量的分数”换来了一个结构性问题（开发集就是测试集）；Harness² 用“测得没那么准的行为对比”换来了一个更干净的设定（真的没有答案）。**

## 我的判断

先声明：这一篇目前只读了论文，判断会偏保守。

1. **它把“没有验证器”当成一等问题，这是对的方向。** 开放世界部署的确没有标准答案，绕开这个前提的方法在真实场景里都会失效。
2. **但“行为对比”的可靠性是这套方法的命门。** 论文用“同模型同环境 + 只保留被证据支持的经验”来兜底，这是一个合理的工程启发式，但它给的是“没变坏”的证据，不是“变好了”的证明。案例里 43.1 → 77.8 很漂亮，但那是一个任务。
3. **消融做得比 RSIGym 实。** 三个组件都有独立贡献，而且和 k 的预算效应分开测了，这一点比“改了一整套框架然后说它有用”要扎实。
4. **成本的口径更诚实。** 它把执行和改进的 token 都算进“计算—性能”曲线，并且落在帕累托前沿上——这比只报“预算花完了没”更有信息量。
